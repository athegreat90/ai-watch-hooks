# Project memory

Native hooks avoid a container startup per event. The installer and image share an exact Python pin and the CLI receives neutral output. The sender filters metadata and does not include prompts or tool arguments. Registrations use absolute paths. Native Codex and Claude registration was verified on the original Windows installation. Other native targets need CI results.

Docs decisions (2026-11-21): doc changes are folded into 1.1.0 (no new version). The two install sections are merged into one Quick start; the event-to-status table mirrors STATES in bridge/hook.py and must be updated with it. Maintainer and CI content lives in docs/MAINTAINING.md. Docker tag is a placeholder. Each repo keeps its own docs with no cross-repo files. Always record decisions here.

Trivy 0.76.2 is pinned by multi-platform image digest. The Zsh scripts resolve the repo from the script location and support overriding the interpreter with AI_WATCH_PYTHON.

HTTPS origin decision (2026-11-22, v1.1.1): `url` may be an https origin (any host name). It uses the default SSL context, so the certificate and host name are verified, with a 2 s timeout for the handshake. Plain http still requires a private IPv4 or loopback, with the 0.5 s timeout. Version 1.1.1 comes from the release automation (patch tag), not a version file.

Base image decision (2026-11-22, v1.1.2): issue #9 lists only HIGH/CRITICAL Debian bookworm CVEs without a published fix, so CI stays green (check_findings.py fails only when a fix exists). Debian trixie was tried (PR #10) and rejected: 51 unique findings on amd64 versus 45 on bookworm, and one already-fixed zlib1g finding made the image check fail. Keep python:3.15.2-slim-bookworm and leave #9 as a tracking issue. The daily report is deduplicated with sort -u.

Standalone install decisions (2026-11-26, v1.2.0): the hooks can be installed without cloning. Chosen: a Python bundle plus `install.sh`/`install.ps1` (behavior unchanged) over a Go rewrite, because the hooks are 480 lines of stdlib Python that already work and a rewrite would need its own parity tests; revisit only if requiring Python becomes a problem. Release assets: `ai-watch-hooks-<tag>.zip` (flat `bridge/*.py`, `VERSION`, installers), `install.sh`, `install.ps1`, `SHA256SUMS` built by `release/assets.sh` (reproducible, fixed timestamps) and uploaded idempotently by `automatic.py publish` (a rerun only adds missing assets). The installers always verify the zip against `SHA256SUMS`. The install folder is fixed (`~/.local/share/ai-watch-hooks`, `%LOCALAPPDATA%i-watch-hooks`) because registrations hold absolute paths; updates replace the code and never touch `config.local.json`. The token is never taken from argv (file, `AI_WATCH_TOKEN` or hidden prompt) and the config is written once. `install.py` ignores the Python pin only when `.python-version` is absent; the standalone installer needs Python 3.8+ and warns outside the tested 3.15.x. Migrating from a clone requires `install.py --uninstall` from the clone first, because uninstall removes only entries ending with its own `hook.py` path (otherwise events are sent twice). URL validation lives in one place, `hook.connect`, exposed to the installers as `install.py --check-url`. The release version now comes from the newest changelog heading when it is higher than the next patch (this supersedes the v1.1.1 note that the version never comes from a file); the unreleased 1.1.2 entry was folded into 1.2.0. The installer tests build the assets and run bash and PowerShell against a local file:// release with a local receiver; `AI_WATCH_TEST_POWERSHELL` selects the PowerShell executable.

Remediation decisions (2026-11-26, v1.2.1): the daily findings issue is created or edited by `security/upsert-issue.sh`, which lists open issues and matches the title exactly. The search API (`gh issue list --search`) found the issues with a user token but nothing in CI, so a new issue was opened every day (#13, #14, #15 duplicate #9, which stays the tracking issue). `security/test_upsert_issue.sh` (stubbed `gh`) runs in CI. The security GitHub App needs Contents, Issues and Pull requests set to Read and write on the installation (a 403 on push and `updateIssue` meant it did not); after fixing that, a manual remediation run edited #9 and opened the base image PR. Release 1.2.1 was only the base image digest refresh.

GitHub App login decision (2026-11-26): `remediate.yml` authenticates `actions/create-github-app-token` with `client-id: vars.SECURITY_APP_CLIENT_ID` (the app's Client ID, `Iv23li...`; not a secret) plus the secret `SECURITY_APP_PRIVATE_KEY`, because the numeric `app-id` input is deprecated. The old `SECURITY_APP_ID` variable is no longer read; delete it once a manual remediation run has succeeded with the new input. The app is `ai-watch-hooks-security`. Branch protection on `main` (applied the same day) requires `native` x4, `images` x2 and `source`, no reviews, admins not enforced, no force pushes or deletions; changes therefore go through a pull request. A runner that never starts a required job (seen once on macOS: cancelled after 15 minutes with no steps) is a capacity issue; rerun the failed job.
